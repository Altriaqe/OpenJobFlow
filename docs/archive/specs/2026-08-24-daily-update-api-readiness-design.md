# JobFlow 每日任务等待 API 就绪设计

## 背景

服务器开机后，`jobflow-daily-update.timer` 可能因 `Persistent=true` 立即补跑。此时 Docker 已启动，但 API 容器仍可能处于应用启动阶段。

2026-08-24 的现场证据如下：

- systemd 在 19:19:07 启动每日任务，19:19:10 以状态码 1 退出；
- 每日脚本输出“AI Agent 快照状态不确定，本次停止”；
- 同一时段 API 日志显示应用正在启动，只有后续健康检查，没有收到 `/reports/daily/status` 请求；
- API 完全就绪后，同一状态查询返回 HTTP 404，符合“当日快照尚不存在”的预期。

根因是每日任务与 API 开机恢复之间的竞态，不是 Tailscale、代理、数据库、Token 或快照数据错误。

## 目标

每日任务在访问快照状态接口前等待 API 就绪，避免开机补跑因 API 尚未启动完成而误判失败。

## 非目标

- 不修改 systemd unit 或 timer；
- 不修改 Docker Compose 启动顺序；
- 不改变抓取范围、ETL、简报生成或 Telegram 投递逻辑；
- 不自动重试任何结果不确定的 Telegram 投递；
- 不在部署后自动触发完整日报。

## 方案

在 `ops/daily_update.sh` 中新增 `wait_for_api_ready` 函数，并在进入项目目录后、检查四个关键词快照前调用。

等待规则：

1. 使用 Ubuntu 主机已有的 `curl` 请求 `http://127.0.0.1:8000/ready`；
2. 单次请求最长等待 3 秒；
3. 请求失败后等待 5 秒再试；
4. 最多尝试 60 次，总等待边界约 5 分钟；
5. 收到成功响应后立即进入现有快照检查流程；
6. 超过等待边界仍未就绪时，输出明确错误并以状态码 1 退出。

## 执行顺序

```text
取得任务锁
  -> 初始化目录与日期
  -> 进入 JobFlow 项目目录
  -> 等待 API /ready
      -> 成功：检查四个关键词快照
      -> 超时：安全退出，不抓取、不写库、不推送
  -> 检查 BOSS 抓取环境
  -> 补抓缺失快照并执行 ETL
  -> 发送一次多关键词图文简报
```

## 错误处理

- API 启动过程中的连接失败、超时和非成功响应均视为“尚未就绪”，在等待窗口内重试；
- 等待超时后只报告 API 未就绪，不把它误报为某个关键词的快照状态异常；
- API 就绪后的快照查询继续沿用现有语义：HTTP 404 表示快照缺失，其他不确定结果停止任务；
- 不输出 `REPORT_TRIGGER_TOKEN` 或其他敏感配置。

## 测试与验收

本地测试应验证：

- 脚本包含 API 就绪等待函数；
- 单次请求超时为 3 秒、重试间隔为 5 秒、最多尝试 60 次；
- API 等待发生在首次 `snapshot_exists` 调用之前；
- 等待失败会阻止后续抓取和推送；
- 现有每日任务脚本测试继续通过；
- `bash -n ops/daily_update.sh` 通过。

服务器部署后先做非投递验收：

- 确认服务器脚本包含等待逻辑；
- 确认 API `/ready` 返回 HTTP 200；
- 确认 timer 下一次触发时间仍为北京时间 09:00；
- 不自动启动完整日报，避免重复抓取或重复推送。

下一次真实定时运行的成功标准：

- `jobflow-daily-update.service` 最终为 `Result=success`、`ExecMainStatus=0`；
- Telegram 只收到一份文字简报和一张配套图；
- 日志不再出现“快照状态不确定”这一开机竞态误报。

## 风险与边界

- 如果 API 在 5 分钟内仍无法就绪，任务会失败并保留明确日志，不会无限等待；
- 本方案依赖 Ubuntu 主机安装 `curl`，当前服务器已通过 `/ready` 验收确认可用；
- 该修复只解决 API 启动竞态，不掩盖 BOSS 登录失效、抓取失败、ETL 失败或 Telegram 投递结果不确定等独立故障。
