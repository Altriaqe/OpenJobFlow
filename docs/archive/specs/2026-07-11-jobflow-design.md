# JobFlow 项目指导规格

> 历史说明：本设计中的 Scrapy/Scrapyd 核心架构已被
> `2026-07-19-production-etl-design.md` 取代。本文件保留用于记录项目最初范围。

日期：2026-07-11
对象：计划在大二寒假投递数据开发、数据分析或爬虫相关实习的学生
可投入时间：暑假每周 15–25 小时

## 项目概要

本项目用于训练并展示一条完整的数据开发链路，而不是只编写单站爬虫脚本。最终成果是一个可以本地一键启动、能够云端演示的自动化招聘数据采集与分析平台。项目主体由学习者逐步实现；指导者负责解释、拆解任务、提供接口和伪代码、设置验收标准、审查代码与协助排错，不直接交付完整项目代码。

## 选定方案

从零实现轻量级单机爬虫工作流平台，技术栈为 Scrapy、Scrapyd、FastAPI、APScheduler、PostgreSQL、Streamlit 和 Docker Compose。

这一方案在原创度、工程含量和暑期完成概率之间最均衡。它覆盖爬虫、SQL、数据管道、后端接口、任务调度、测试和部署，同时避开 Celery、Redis、多节点 Worker、复杂权限和前端框架带来的过早复杂度。

参考项目只用于理解设计：

- [Scrapy](https://github.com/scrapy/scrapy)：学习爬虫框架核心机制。
- [Scrapyd](https://github.com/scrapy/scrapyd)：学习爬虫部署和任务执行接口。
- [Gerapy](https://github.com/Gerapy/Gerapy)：参考爬虫管理平台的功能划分。
- [Crawlab](https://github.com/crawlab-team/crawlab)：参考成熟平台的任务、节点和日志设计。

不直接套壳或大规模复制上述项目，保证学习者能够解释自己的核心代码。

## 项目定位

项目暂定名为 `JobFlow——自动化招聘数据采集与分析平台`。

系统完成以下数据流：

```text
数据源配置 -> 定时采集 -> 清洗校验 -> 去重入库
           -> 状态监控 -> 查询导出 -> 趋势分析
```

最终成果包括：

1. 自动化爬虫工作流主项目。
2. 基于采集结果的招聘岗位技能分析模块。
3. 本地 Docker Compose 一键启动能力。
4. 云端 API 文档和 Streamlit 仪表盘。
5. 自动化测试、README、架构说明和演示视频。

## 范围

### 第一版包含

- 管理数据源及启用状态。
- 手动启动爬虫任务。
- 使用 Cron 规则定时启动任务。
- 记录任务状态、时间、数据量和错误摘要。
- 字段清洗、薪资标准化、技能提取和幂等去重。
- 查询岗位、任务记录和失败日志的 REST API。
- 技能、城市和薪资趋势的 Streamlit 分析页面。
- Docker Compose 服务编排和云端部署。
- 一个本地模拟招聘数据源和两个合规公开数据源。

### 第一版不包含

- 登录注册和多用户权限。
- Vue、React 等复杂管理前端。
- Redis、Celery、多节点 Worker 和分布式调度。
- 代理池、验证码绕过、登录破解或高频访问。
- 自动生成任意网站爬虫的低代码设计器。

## 合规边界

只使用公开 API、RSS、明确允许访问的公开页面、本地模拟站点或获得授权的数据源。每个真实数据源必须在 README 中记录来源、访问方式、频率限制和使用说明。遵守 robots.txt、网站条款和适用法律；不采集个人敏感信息，不绕过访问控制。

## 系统架构

```text
公开 API / RSS / 合规网页
           |
           v
      Scrapy Spider <--- Scrapyd <--- APScheduler <--- FastAPI
           |
           v
 清洗 / 校验 / 去重 Pipeline
           |
           v
      PostgreSQL <--- FastAPI 查询接口
           |
           v
   Streamlit 分析仪表盘
```

### 组件职责

- `Scrapy`：请求、分页、解析和生成结构化 Item。
- `Pipeline`：字段标准化、校验、技能提取、去重和入库。
- `Scrapyd`：部署和运行爬虫，返回任务标识及运行状态。
- `APScheduler`：解释 Cron 规则并按时向 Scrapyd 提交任务。
- `FastAPI`：管理数据源、计划任务、运行记录和岗位查询。
- `PostgreSQL`：保存业务数据、元数据和任务历史。
- `Streamlit`：展示分析结果，不承担任务控制功能。
- `Docker Compose`：统一启动 API、调度器、Scrapyd、数据库和仪表盘。

## 模块边界

1. 采集模块只负责把外部数据转换为统一 Item，不直接实现分析页面。
2. 数据处理模块通过固定字段协议接收 Item，避免与具体 Spider 耦合。
3. 调度模块只决定何时启动任务，不实现网页解析。
4. API 模块通过服务层访问数据库和 Scrapyd，不依赖 Spider 内部代码。
5. 分析模块只读取清洗后的数据库表，不读取爬虫临时文件。

## 核心数据表

### `data_sources`

保存数据源名称、类型、基础地址、对应 Spider 名称、启用状态、抓取间隔及创建时间。

### `crawl_schedules`

保存数据源、Cron 表达式、启用状态、最近运行时间和下一次运行时间。

### `crawl_runs`

保存一次运行对应的数据源、Scrapyd Job ID、状态、开始与结束时间、抓取数量、成功写入数量和错误摘要。

状态至少包括：`queued`、`running`、`succeeded`、`failed` 和 `cancelled`。

### `jobs`

保存来源、外部岗位 ID、职位名称、公司、城市、薪资下限、薪资上限、描述、原始 URL、发布时间、内容哈希、首次发现时间和最后发现时间。

优先使用 `(source_id, external_job_id)` 唯一约束；无外部 ID 时使用稳定内容哈希进行幂等去重。

### `job_skills`

保存岗位与标准技能名称的多对多关系。第一版使用可解释的技能词典和规则提取，不引入大模型调用。

## 第一版 API 范围

- 数据源：创建、查询、更新启用状态。
- 计划任务：创建、查询、启用和停用。
- 运行任务：立即启动、查询列表、查询单次详情。
- 岗位数据：分页查询，按城市、技能和薪资范围筛选。
- 健康检查：检查 API 是否可用；进阶检查数据库和 Scrapyd 依赖。

第一版不实现通过 API 任意上传 Python 代码，避免安全风险和范围膨胀。

## 异常处理

- 网络超时和 `5xx` 使用指数退避，最多重试三次。
- `404` 和解析规则失效不盲目重试，记录 URL 和错误类型。
- 字段缺失时保存原始上下文并标记数据质量异常。
- 同一数据源已有任务运行时拒绝重复启动，防止任务重叠。
- 数据库批次写入失败时回滚事务，避免部分提交。
- Spider 异常结束时将运行记录更新为 `failed` 并保存错误摘要。
- 服务重启后，业务数据和历史运行记录必须保留。
- 日志不得记录密码、密钥、数据库连接串或其他敏感信息。

## 测试策略

1. 解析测试：使用本地 HTML/JSON fixture 验证字段解析，不依赖实时网站。
2. 数据处理测试：覆盖薪资转换、技能提取、字段校验和幂等去重。
3. API 测试：使用测试客户端验证状态码、响应结构和错误分支。
4. 集成测试：验证模拟数据源经过 Scrapy、Pipeline 和 PostgreSQL 后能被 API 查询。
5. 启动测试：验证 Docker Compose 在干净环境中能够启动全部必要服务。

不强求虚高的覆盖率数字；优先覆盖清洗、去重、状态流转和错误分支等高风险逻辑。

## 第一版验收标准

- Docker Compose 能用一条命令启动全部必要服务。
- 接入一个本地模拟源和两个合规公开源。
- 定时任务连续运行七天，无无限重试或重复任务失控。
- 对同一批数据重复采集时不产生重复岗位。
- 主要解析、清洗、去重和 API 行为有自动化测试。
- README 能让另一位同学在新环境中独立启动项目。
- 云端可以访问 API 文档和 Streamlit 仪表盘。
- 每个公开数据源都有合规说明。

## 八周路线

| 周次 | 学习与实现内容 | 验收成果 |
|---|---|---|
| 1 | HTTP、HTML、CSS/XPath、异常、日志、pytest | Requests 小爬虫、JSON 输出、至少 5 个有效测试 |
| 2 | Scrapy Spider、Item、Pipeline、中间件 | 模拟招聘站点爬虫、分页采集、结构化输出 |
| 3 | PostgreSQL、表设计、SQLAlchemy、Alembic | 五张核心表、数据入库和常用 SQL 查询 |
| 4 | 清洗、薪资标准化、技能提取、哈希去重 | 重复运行无重复数据，接入第一个公开源 |
| 5 | FastAPI、REST、Pydantic、Scrapyd | API 启动任务并查询状态、岗位和运行记录 |
| 6 | APScheduler、Cron、任务锁和失败重试 | 自动调度、错误日志、第二个公开源 |
| 7 | Pandas、Streamlit、Docker Compose | 分析仪表盘和本地一键启动 |
| 8 | 云服务器、Nginx、环境变量、GitHub Actions | 在线演示、自动测试、README 和演示视频 |

每周时间建议：学习 30%、编码 60%、复盘与文档 10%。

## 逐微任务指导协议

每个任务预计 1–3 小时，并且只在上一步验收通过后发布下一步。每个任务包含：

1. 本步目标和系统增量。
2. 只覆盖当步所需的前置知识及学习资料。
3. 需要创建或修改的文件位置。
4. 类、函数、字段和接口的编写顺序。
5. 接口定义、伪代码或局部示例，不直接交付完整项目答案。
6. 运行及测试命令。
7. 可观察、可复现的验收标准。
8. 推荐的 Git 提交信息。
9. 学习者提交代码或报错后进行检查、解释和纠错。

排错时先解释错误所在层级和排查顺序；学习者经过合理尝试仍无法解决时，再逐步提高提示具体程度。项目核心代码始终由学习者完成。

## Git 约定

每周保留 3–5 个有意义的提交，使用能说明改动目的的消息，例如：

```text
feat: add mock job spider with pagination
feat: normalize salary fields in item pipeline
test: cover duplicate job detection
fix: mark crawl run failed when parser raises error
docs: add local deployment instructions
```

禁止在仓库中提交 `.env`、API 密钥、数据库密码、虚拟环境、原始大数据文件或日志文件。

## 简历呈现原则

简历强调完整链路、关键设计选择和可验证结果。数据量、任务成功率、测试覆盖率和性能指标必须在项目真实运行后统计，不预先编造。

可在项目完成后根据真实结果改写为：

> 独立设计并实现自动化招聘数据采集平台，基于 Scrapy/Scrapyd 完成多源增量采集，通过 APScheduler 实现定时调度与失败重试；使用 PostgreSQL 完成数据建模、清洗和幂等去重，并通过 FastAPI、Streamlit 提供数据查询与岗位技能趋势分析；使用 Docker Compose 完成服务编排和云端部署。

## 已知风险

- 公开数据源可能变更结构、停用接口或调整访问条款，因此以适配器隔离，并保留本地 fixture 与模拟源保证演示稳定。
- 云服务器可能产生少量费用；部署前再选择具体平台和预算。
- 八周计划依赖每周稳定投入。若进度落后，优先保留采集、入库、调度、测试和 README，缩减仪表盘视觉效果与高级部署功能。
- 招聘数据的薪资和技能字段质量不统一，规则提取结果必须说明局限，不包装为精确结论。
