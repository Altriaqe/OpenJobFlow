# JobFlow 平台化演进设计

日期：2026-07-30

## 1. 设计目标

JobFlow 的长期目标不是单独完成一个招聘爬虫，而是建设一个面向数据开发实践的轻量 AI 数据中台。系统负责把招聘数据采集、清洗、分析和入库，之后通过只读分析 API 为 AI 总结服务和微信机器人等外部渠道提供结构化数据。

核心链路如下：

```text
本地快照 / 动态数据源
        ↓
Source Adapter
        ↓
ETL Worker：校验、清洗、标准化、去重、入库
        ↓
PostgreSQL：ops / raw / core / mart
        ↓
只读语义查询 API
        ↓
AI Summary Service
        ↓
微信机器人 / 其他消息渠道
```

## 2. 模块职责

### Source Adapter

当前阶段使用本地招聘数据快照，重点验证字段映射、数据质量和 ETL 流程。后续接入动态爬取或合规 API 时，只新增或替换 Adapter，不修改数据库、查询层和机器人层。

动态采集必须遵守数据源的使用条款、robots.txt、访问频率限制和隐私边界。真实数据源的授权情况、采集时间和字段范围需要记录在数据源文档中。

### ETL Worker

负责批次运行、原始数据保存、结构校验、字段清洗、标准化、幂等 Upsert、质量统计和失败记录。Worker 是唯一允许执行采集和数据库写入的运行组件。

### PostgreSQL

数据库按职责分为四层：

- `ops`：数据源、批次、运行状态和错误信息。
- `raw`：保留可追溯的原始记录。
- `core`：统一岗位模型、技能和岗位技能关系。
- `mart`：面向分析的城市、薪资和技能聚合指标。

AI 和机器人默认只读取 `mart`，必要时经过白名单授权读取脱敏后的 `core`，不得直接访问 `raw`。

### 只读语义查询 API

API 为调用方提供动态但受控的查询能力。调用方可以选择允许的维度、指标、过滤条件、排序方式和时间范围，服务端负责把查询协议转换成参数化 SQL。

示例请求：

```json
{
  "dimensions": ["city", "job_category"],
  "metrics": ["job_count", "avg_salary"],
  "filters": {
    "city": ["上海", "杭州"],
    "date_range": "last_7_days"
  },
  "limit": 20
}
```

查询协议必须使用字段白名单。禁止调用方传入任意表名、任意字段名、原始 SQL、写操作或未授权的数据范围。服务端还需要校验最大返回行数、时间范围、排序字段和查询频率。

### AI Summary Service

AI 服务只接收语义查询返回的结构化结果和指标口径，不直接连接数据库。它负责：

1. 根据查询结果生成岗位市场摘要。
2. 标注统计时间范围、数据源和指标口径。
3. 区分事实、计算结果和推测，不能补造不存在的数据。
4. 在数据不足、查询失败或指标不适用时明确报告限制。

AI 服务不负责爬取、清洗、写库或修改业务数据。

### 机器人渠道适配器

微信机器人只是一个外部只读客户端。它通过 API 发起受控查询，接收 AI Summary Service 的结果并发送汇报。后续可以用相同接口扩展到钉钉、飞书、网页或命令行客户端。

机器人不得：

- 直接连接 PostgreSQL。
- 执行任意 SQL。
- 触发写库、删除或修改操作。
- 绕过查询白名单访问原始数据。
- 把 Cookie、Token、数据库密码或原始岗位敏感信息发送到消息渠道。

## 3. 数据流与权限边界

```text
采集 / 导入命令
        │ 写入权限
        ▼
ETL Worker ───────► PostgreSQL raw/core/mart
                          │
                          │ 只读权限
                          ▼
                  Semantic Query API
                          │
                          ▼
                  AI Summary Service
                          │
                          ▼
                    微信机器人
```

权限设计遵循“写入和读取分离”：Worker 使用写入凭据，API 使用只读凭据，AI 服务和机器人只能调用 API。即使机器人凭据泄漏，也不应获得数据库写入能力。

## 4. 数据源演进路线

### 阶段一：本地数据源

- 使用本地快照或人工构造 fixture。
- 验证 Adapter、字段映射、质量校验和 ETL 入库。
- CI 和单元测试不依赖真实外部网络。

### 阶段二：受控动态数据源

- 接入明确授权的公开 API、RSS 或允许访问的页面。
- 配置请求频率、超时、重试和失败日志。
- 为每个来源维护独立 Adapter 和合规说明。

### 阶段三：生产化数据源

- 通过环境变量配置凭据和来源参数。
- 采集任务由 Worker 调度。
- 对数据源变化、授权范围、保存期限和删除请求建立记录。

无论数据源如何变化，下游都只依赖统一岗位模型和语义查询层。

## 5. 分阶段实施顺序

1. 完成当前本地快照到统一 `JobRecord` 的质量校验。
2. 建立 PostgreSQL `ops/raw/core` 基础表和幂等入库。
3. 建立 `mart` 聚合指标和只读分析 API。
4. 完成 AI Summary Service 的结构化输入、事实约束和错误处理。
5. 接入一个机器人渠道，先实现手动查询和手动汇报。
6. 增加定时汇报、任务状态和消息发送日志。
7. 在合规条件满足后替换或新增动态数据源 Adapter。
8. 使用 Docker Compose 部署 PostgreSQL、Worker、API、Dashboard 和 AI 服务。

每个阶段都必须有自动化测试、可复现命令、真实运行结果和对应 Git 提交。

## 6. 简历呈现原则

项目完成后，简历可以围绕以下真实能力展开：

- 设计 Source Adapter，隔离数据源变化与下游数据模型。
- 建设 raw/core/mart 分层数据链路。
- 通过幂等 Upsert 和批次日志保证重复运行可追溯。
- 设计带字段白名单的动态分析查询 API。
- 构建只读 AI 汇报链路并接入机器人渠道。
- 使用测试、Docker 和运行指标证明系统可复现。

简历中的数据量、处理耗时、成功率、去重数量和 API 响应时间只使用真实测试或运行记录，不编造指标。

## 7. 风险与暂缓项

- 未获得明确授权前，不把受限招聘数据部署到公开服务。
- AI 输出必须保留数据时间范围和指标口径，避免生成无依据结论。
- 动态字段不能演变为任意 SQL 执行入口。
- 机器人接入先采用只读和低权限设计，认证、限流和审计逐步补齐。
- 不在当前阶段引入 Redis、Celery、分布式 Worker 或复杂多 Agent 架构。
