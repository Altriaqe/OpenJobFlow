# JobFlow V1.3.1 多关键词岗位趋势简报 PRD

日期：2026-08-20
状态：设计已确认，等待实施计划
版本：V1.3.1

## 1. 背景

V1.3 只采集 `AI Agent` 一个关键词，并对上海、北京、杭州、深圳各抓取三页。四个城市都抓满相同页数时，每城样本数相同，城市岗位占比图固定为 25%，无法有效表达岗位方向与城市之间的差异。

V1.3.1 将关键词扩展为四个岗位方向，保留现有四城市、每组抓取三页的规则。系统按关键词建立独立每日快照，再把四个关键词相较前日的变化汇总为一份 Telegram 简报和一张“关键词 × 城市”新增岗位热力图。

## 2. 目标

- 每天自动采集四个岗位关键词；
- 每个关键词继续覆盖四个城市、每城三页；
- 每个关键词建立独立、不可重复的每日快照；
- 比较同一关键词、同一城市相较前一自然日的新增岗位数；
- 用一份文字简报说明不同岗位方向的日趋势和城市优势；
- 用一张热力图展示“哪个岗位方向在哪个城市新增更多”；
- 保留失败重试、断点恢复和 Telegram 防重复发送能力。

## 3. 非目标

V1.3.1 不包含：

- 不改变城市范围；
- 不改变每城三页的抓取深度；
- 不抓取岗位详情页；
- 不宣称样本数量等于招聘市场完整岗位总量；
- 不使用 AI、机器学习或复杂规则自动分类岗位；
- 不把四个关键词的岗位数直接相加为“全市场唯一岗位总数”；
- 不新建统一大宽表，不重构现有快照表；
- 不调整 systemd 的 45 分钟超时，真实超时后再单独处理。

## 4. 固定采集范围

关键词按以下顺序处理：

1. `AI Agent`
2. `Python开发`
3. `Java开发`
4. `数据分析`

城市保持：

1. 上海
2. 北京
3. 杭州
4. 深圳

每个“关键词 × 城市”抓取三页，理论上每天最多处理：

```text
4 个关键词 × 4 个城市 × 3 页 = 48 页
```

数据口径统一表述为“固定范围抓取样本”或“样本需求信号”。

## 5. 数据模型

V1.3.1 复用现有表，不新增数据库迁移：

```text
core.job_snapshots
└─ 每个日期、每个关键词一份独立快照

core.job_snapshot_items
└─ 保存对应快照中的岗位

ops.report_deliveries
└─ 保存 Telegram 文字和图片的投递状态
```

现有数据库已经具备：

```sql
UNIQUE (snapshot_date, search_keyword)
```

用于防止同一天重复创建同一关键词快照；并已有：

```sql
INDEX (search_keyword, snapshot_date DESC)
```

用于按关键词读取历史快照。

同一个岗位可能被多个搜索关键词命中。V1.3.1 在每个关键词内部按岗位身份去重，但不跨关键词删除记录，因为跨关键词命中本身代表搜索相关性。简报不得把四组结果直接相加后称为唯一市场岗位总量。

## 6. 每日处理流程

```text
systemd timer 触发
→ 获取当天四关键词快照状态
→ 已存在的关键词跳过抓取
→ 只抓取缺失关键词
→ 每个关键词分别合并四城市 JSON
→ 每个关键词分别执行 ETL 并建立快照
→ 确认四份快照全部成功
→ 分别加载同关键词前一自然日快照
→ 计算关键词 × 城市新增岗位数
→ 生成一份合并简报
→ 有完整前日基线时生成热力图，否则生成“趋势基线建立中”提示图
→ Telegram 发送一次文字和一次图片
```

某个关键词失败时，不发送不完整简报。其他成功快照保留；下次重跑只补缺失关键词。

## 7. 趋势口径

热力图单元格定义为：

```text
当天该关键词、该城市出现的岗位身份
减去
前一自然日同关键词、同城市已经出现的岗位身份
```

岗位身份沿用现有 `source + external_id` 规则。图中数值表示“相较前一自然日新增采集到的唯一岗位数”。

如果某个关键词缺少前一自然日、相同采集范围的快照，则该关键词没有有效日趋势基线。四个关键词任一缺少基线时，当天简报标注“趋势基线建立中”，并发送一张不包含趋势数字的基线提示图，不生成容易误解的增减热力图。

## 8. 合并文字简报

简报保持一条 Telegram 文字消息，结构为：

```text
JobFlow｜多岗位招聘趋势日报
日期：YYYY-MM-DD

【岗位趋势】
AI Agent：较昨日新增采集 X 个，新增最多城市：上海
Python开发：较昨日新增采集 X 个，新增最多城市：深圳
Java开发：较昨日新增采集 X 个，新增最多城市：北京
数据分析：较昨日新增采集 X 个，新增最多城市：杭州

【城市优势】
上海：AI Agent 新增样本最多
北京：Java开发新增样本最多
杭州：数据分析新增样本最多
深圳：Python开发新增样本最多

【数据口径】
4 个关键词 × 4 个城市 × 每组 3 页
数据表示固定范围抓取样本，不代表全市场总量
同一岗位可能被多个关键词命中
```

这里的 X 是当天出现、前一自然日同关键词快照中没有出现的岗位身份数量，不是两个固定页数样本总量的差。实际文案只陈述数据能够支持的事实。某城市或关键词并列第一时明确写“并列”，不强行选择一个结果。

## 9. 热力图

图表使用 Matplotlib 生成 PNG，并通过 Telegram 随简报发送。

- 纵轴：`AI Agent`、`Python开发`、`Java开发`、`数据分析`；
- 横轴：上海、北京、杭州、深圳；
- 单元格数值：相较前日新增的唯一岗位数；
- 颜色：数值越大，颜色越深；
- 标题：`多岗位城市新增趋势`；
- 图下注明：`固定范围抓取样本，不代表全市场总量`。

V1.3 的城市岗位占比饼图由该热力图替代，不再推送固定为 25% 的饼图。

首日或任一关键词缺少有效前日基线时，图片只显示“趋势基线建立中”和“完成下一自然日采集后生成热力图”，不显示增减数字。这样既不伪造趋势，也能满足现有投递状态对文字和图片都成功的完成条件。

## 10. 周趋势

周日继续执行“本周与上一完整周”比较，但改为按关键词分别生成简短结论。只有四个关键词都具备两周完整、相同范围的快照时才输出周趋势；否则明确写“周趋势数据不足”，不使用残缺周期计算。

## 11. 投递与幂等

四份关键词快照共同组成当天的一份合并简报。投递状态遵循以下规则：

- 四份快照都存在后才允许发送；
- 文字发送成功后记录文字消息 ID；
- 图片发送成功后记录图片消息 ID；
- 文字成功、图片失败时，下次只补发图片；
- 四份快照均已完成投递时返回 `already_sent`；
- 重跑不得重复抓取已存在快照，不得重复发送已完成内容。

V1.3.1 不新增投递表。合并投递成功后，四个快照对应的投递状态保持一致，并记录同一组 Telegram 消息 ID。

## 12. 错误处理

- BOSS 登录检查失败：停止任务，不写入新快照；
- 单个关键词抓取失败：保留其他已成功快照，不发送合并简报；
- 单个关键词 ETL 失败：事务回滚该批次，任务返回失败；
- 四份快照范围不一致：拒绝比较和发送；
- Telegram 文字失败：记录失败状态，任务返回失败；
- Telegram 图片失败：保留文字成功状态，下次只补图片；
- 总运行时间超过 45 分钟：由 systemd 判定失败，保留日志，后续单独优化。

## 13. 测试与验收

### 本机自动化测试

- 四关键词配置与循环顺序；
- 已存在关键词跳过、缺失关键词补抓；
- 四份独立快照创建；
- 同关键词前日比较；
- 关键词 × 城市新增矩阵；
- 并列城市优势文案；
- 首日无基线文案和基线提示图；
- 热力图 PNG 可生成且资源正确关闭；
- 四份快照缺一时拒绝发送；
- 文字成功、图片失败后的补发；
- `already_sent` 防重复；
- Shell 契约、Ruff、格式和全仓库回归测试。

### Ubuntu 真实验收

```text
4 关键词 × 4 城市 × 3 页抓取完成
4 份独立快照成功入库
合并文字简报真实到达 Telegram
首日正确收到“趋势基线建立中”文字和提示图
第二个自然日起热力图真实到达 Telegram
脚本退出码为 0
总运行时间不超过 45 分钟
```

不能用离线测试代替 Ubuntu、BOSS、PostgreSQL 和 Telegram 的真实验收。

## 14. 完成标准

只有同时满足以下条件，才可称为 V1.3.1 完成：

1. 本机自动化测试和静态检查通过；
2. Ubuntu 完成四关键词真实抓取和四份快照入库；
3. Telegram 真实收到一份合并文字简报；
4. 第二个自然日真实收到新增岗位热力图；
5. 重跑验证不会重复抓取和重复发送；
6. README、架构、Ubuntu 部署和交接文档按实际验收结果更新。

## 15. 后续版本候选项

后续大版本可再评估统一岗位事实模型、跨关键词命中关系、关键词与城市联合分析索引，以及更长周期的岗位需求趋势。该内容不属于 V1.3.1，不在本轮提前实现。
