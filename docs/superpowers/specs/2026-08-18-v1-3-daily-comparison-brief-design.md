# JobFlow V1.3：每日招聘数据对比简报 PRD

## 1. 文档目的

本文档定义 JobFlow V1.3 的产品目标、数据口径、抓取扩围、每日与每周对比、Telegram 图文推送、异常处理、历史数据回填和验收标准。

本文档只表示设计已经确认，不表示功能已经编码、离线测试通过、部署到 Ubuntu 或完成真实外部服务验收。

## 2. 已验证的 V1.2 基线

截至 2026-08-18，现有系统已经在 Ubuntu 上打通以下正式链路：

```text
systemd timer
→ Ubuntu Chrome + Xvfb + CDP 登录态
→ boss-zhipin-scraper
→ 四城市 JSON 原子快照
→ JobFlow ETL
→ PostgreSQL
→ 固定规则中文查询简报
→ Ubuntu 服务器侧 Mihomo 代理
→ Telegram 私聊
```

Windows 本地机关机、Windows 本地代理关闭时，Ubuntu 服务器仍可通过服务器侧代理完成正式定时推送。

V1.2 当前限制：

- 自动任务只搜索单一关键词 `AI Agent`；
- 城市固定为上海、北京、杭州、深圳；
- 每个城市只抓取 1 页；
- 简报主要查询累计数据库聚合结果；
- 没有不可变的每日岗位成员快照；
- 没有日环比和完整自然周环比；
- Telegram 只发送文字，没有发送统计图。

## 3. V1.3 产品目标

### 3.1 核心目标

将 JobFlow 从“显示当前累计结果”升级为“保存每日真实岗位采集快照并发送可追溯的对比简报”。

每日任务完成后，用户应在 Telegram 收到：

```text
完整中文文字简报
→ 当天城市岗位占比饼图
```

文字简报需要回答：

- 今天采集到多少去重岗位；
- 相较前一自然日发生了什么变化；
- 每个城市发生了什么变化；
- 哪些技能出现较多以及如何变化；
- 月薪制岗位的典型薪资如何变化；
- 哪些岗位是新增采集、连续出现或本次未出现；
- 周日时，本完整自然周相较上一完整自然周发生了什么变化。

### 3.2 成功定义

V1.3 成功必须同时满足：

```text
每城 3 页真实岗位列表采集成功
+ 四城市整批原子入库成功
+ 每日岗位成员快照可追溯
+ 日环比计算正确
+ 周日完整自然周环比计算正确
+ Telegram 文字真实送达
+ Telegram 饼图真实送达
+ 五分钟临时 timer 无人操作自动触发成功
```

## 4. 产品范围

### 4.1 V1.3 必须实现

- 单一关键词 `AI Agent`；
- 上海、北京、杭州、深圳四个城市；
- 每个城市从 1 页扩大到 3 页；
- 继续使用 `--no-detail`，不逐个打开岗位详情页；
- 四城市全部成功后才生成正式快照；
- 保存每日快照头和每日岗位成员明细；
- 数据模型预留 `search_keyword` 维度；
- 日环比；
- 周日追加完整自然周环比；
- 城市、技能、薪资和岗位快照变化；
- 城市岗位占比饼图；
- Telegram 先发送文字，再发送图片；
- 消息分阶段重试和防重复发送；
- 历史批次只读审计与有条件回填；
- 单元测试、数据库集成测试、离线 Telegram 测试和 Ubuntu 真实验收。

### 4.2 V1.3 明确不包含

- 实际增加第二个或更多搜索关键词；
- 抓取岗位详情页和完整 JD；
- 扩展到新的城市；
- 浏览器数据看板或管理后台；
- Telegram 对话命令，例如发送“今日总结”触发查询；
- 将规则统计包装成已经调用大模型生成的结论；
- 自动推断岗位真实发布时间或真实下线时间；
- 自动绕过登录、验证码或平台风控；
- 用大模型推测岗位变化的业务原因；
- 与 V1.3 无关的公网域名、HTTPS、备份平台或权限系统。

## 5. 真实岗位数据与表达边界

V1.3 数据来自真实招聘岗位列表，因此可以使用“岗位”“真实岗位数据”等业务表述。

但是抓取结果是特定时间、关键词、城市和页数下的采集快照，不等同于目标平台全部岗位，也不能证明岗位的真实生命周期。因此统一使用：

```text
今日新增采集岗位
连续出现岗位
本次未出现岗位
```

禁止直接将“本次未出现”写成“岗位已经下线”。

## 6. 抓取范围与成功门槛

### 6.1 固定抓取范围

```text
关键词：AI Agent
城市：上海、北京、杭州、深圳
每城页数：3
详情页：不抓取（--no-detail）
```

岗位名称、公司、城市、薪资和技能标签仍来自真实岗位列表。`--no-detail` 只表示不逐个打开完整岗位说明页。

### 6.2 整批原子规则

以下条件全部满足后，才允许写入当天正式快照：

```text
Chrome/CDP 登录检查成功
四个城市的抓取命令全部退出为 0
四份 JSON 全部存在且可解析
四个城市均返回非空岗位列表
合并数据可以通过 JobFlow Adapter 校验
ETL 批次成功提交
```

任一城市失败、JSON 不合法或出现异常空结果时：

- 整批停止；
- 不写入当天正式快照；
- 不计算当天对比；
- 不发送可能误导的简报；
- 保留上一份有效快照和数据库数据；
- 日志记录失败阶段和错误类型。

## 7. 选定的数据方案

### 7.1 方案结论

V1.3 采用“每日快照头 + 快照岗位明细 + 投递状态”的方案。

不采用只保存聚合指标的方案，因为它无法可靠计算周内岗位去重以及新增采集、连续出现、本次未出现。

不采用每次从 `raw.job_records` 动态重算的方案，因为历史批次的关键词和完整性边界不够清晰，长期查询和维护成本较高。

### 7.2 每日快照头

每日快照头至少表达：

- 快照唯一标识；
- 快照自然日期；
- 搜索关键词；
- 关联的成功 ETL 批次；
- 实际完成时间；
- 城市数量；
- 抓取页数；
- 城市集合；
- 是否包含详情页；
- 正式快照状态。

同一自然日期、同一搜索关键词只能有一份正式成功快照。

### 7.3 快照岗位明细

每条快照岗位明细至少表达：

- 所属快照；
- `source`；
- `external_id`；
- 岗位名称；
- 公司；
- 城市；
- 原始薪资文本；
- 标准化薪资上下限、单位和薪数；
- 技能数组；
- 当次采集时间。

岗位在一个快照内按 `source + external_id` 去重。

`core.jobs` 继续表示已知岗位的当前标准化状态；新的每日快照明细用于表达“某个岗位在某一天的采集结果中是否出现”，两者职责不能混用。

### 7.4 多关键词预留

V1.3 只实际运行 `AI Agent`，但快照头必须保存 `search_keyword`。

同一物理岗位未来可能被多个搜索关键词命中。岗位实体仍按 `source + external_id` 识别，关键词属于快照与岗位成员之间的采集上下文，不能把同一岗位复制成多个实体。

### 7.5 投递状态

每份正式快照需要记录 Telegram 投递状态，至少区分：

```text
pending
text_sent
completed
partial_failed
failed
```

同时保存文字消息 ID、图片消息 ID、尝试次数和最后错误类型。不得保存 Bot Token、代理订阅或其他敏感值。

## 8. 数据处理流程

```text
systemd timer
→ 获取任务锁
→ 检查 Chrome/CDP 登录态
→ AI Agent × 四城市 × 每城 3 页 × no-detail
→ 四城市输出校验
→ 合并并按 source + external_id 去重
→ Adapter 校验与 ETL
→ 在事务中写入成功批次、每日快照头和岗位明细
→ 读取前一自然日快照
→ 计算日环比
→ 如果当天为周日，计算完整自然周环比
→ 生成中文文字简报
→ 生成城市岗位占比 PNG
→ Telegram 发送文字
→ Telegram 发送图片
→ 记录投递状态和 systemd 日志
```

数据入库和消息投递是两个阶段。Telegram 失败不能回滚已经成功写入的真实岗位快照。

## 9. 日环比口径

### 9.1 比较日期

日环比固定为：

```text
当天成功快照 vs 前一自然日成功快照
```

两个快照还必须具备完全相同的搜索关键词、城市集合、每城页数和详情页模式。只要任一采集范围不同，就显示“暂无同口径历史基准”。

如果前一自然日没有成功快照，显示“暂无历史基准”，不得自动寻找更早日期替代。

### 9.2 岗位数量

当天岗位总量为当天快照内按 `source + external_id` 去重后的岗位数。

```text
绝对变化 = 当天岗位数 - 前一自然日岗位数
变化率 = 绝对变化 / 前一自然日岗位数 × 100%
```

当前一自然日岗位数为 0 时，只显示绝对新增数量，变化率显示“不适用”。

### 9.3 岗位集合变化

设当天岗位集合为 `D`，前一自然日岗位集合为 `P`：

```text
新增采集 = D - P
连续出现 = D ∩ P
本次未出现 = P - D
```

### 9.4 城市变化

按每个城市分别计算：

- 当天去重岗位数；
- 相较前一自然日的绝对变化；
- 前日非 0 时的变化率。

四城市当日岗位数之和必须与当天总岗位数一致。若同一岗位异常出现在多个城市，只按快照中已标准化并通过校验的单一城市归属统计。

### 9.5 热门技能变化

热门技能按“包含该技能的去重岗位数”统计：

- 同一岗位的同一技能只计一次；
- 默认展示当天 Top 5；
- 同时展示相较前一自然日的岗位数变化；
- 技能名称沿用 Adapter 清洗后的标准文本；
- 不从未抓取的完整 JD 中推测技能。

### 9.6 月薪中位数变化

薪资只统计 `salary_unit = K_PER_MONTH` 且上下限有效的岗位。

单条岗位先计算：

```text
月薪区间中点 = (salary_min + salary_max) / 2
```

再对当天所有符合条件的去重岗位计算中位数。日薪和时薪不混入月薪比较。

当有效月薪样本为空时显示“暂无有效月薪样本”，不输出 0K。

## 10. 完整自然周环比口径

### 10.1 触发规则

周环比只在周日当天每日更新完成后追加。

```text
本周：当天所在自然周的周一至周日
上一周：前一个完整自然周的周一至周日
```

周一至周六不展示不完整周环比。

两个自然周内的每日快照必须使用相同的搜索关键词、城市集合、每城页数和详情页模式；存在不同口径快照时，不生成周环比。

### 10.2 周岗位去重

自然周内多天出现的同一岗位，按 `source + external_id` 只计算一次。

周维度的城市、技能和薪资描述属性使用该岗位在该周最后一次成功快照中的标准化值，避免同一岗位按出现天数重复加权。

### 10.3 周报指标

周日追加：

- 本周去重岗位总量；
- 相较上一完整自然周的绝对变化和变化率；
- 四城市周岗位变化；
- Top 5 热门技能及变化；
- 月薪制岗位薪资中位数及变化。

如果上一完整自然周数据不完整，显示“暂无完整周基准”，不得用零散日期拼接或用七天前单日数据替代。

## 11. 中文简报结构

### 11.1 每日文字简报

单条文字简报按以下顺序生成：

```text
标题与快照日期
采集范围说明
核心岗位总量与日环比
城市岗位变化
岗位快照变化
热门技能变化
月薪中位数变化
数据观察与口径提示
周日时追加完整自然周对比
```

文字必须保持在 Telegram 单条 `sendMessage` 的 4096 字符限制以内。首版采用 Top 5 和固定字段控制长度，不拆成多条文字消息。

“数据观察”由确定性规则根据已计算指标生成，只能描述上升、下降、持平、城市占比等可验证事实，不得编造变化原因。

现有可选大模型报告能力不属于 V1.3 的验收依赖。V1.3 即使不调用外部大模型，也必须可以完整生成和发送对比简报。

### 11.2 周日简报

周日简报在每日模块后追加周环比模块，不单独发送另一份周报。

### 11.3 已选格式：管理驾驶舱

V1.3 已选择“管理驾驶舱”格式，遵循“先结论、再指标、后明细”的阅读顺序：

- 使用 Telegram 现有纯文字能力，不依赖 Markdown、HTML、颜色或等宽表格；
- 上涨使用 `↑`，下降使用 `↓`，无变化使用“持平”；
- 缺少比较基准时显示“暂无历史基准”；
- “管理摘要”和“周度观察”由确定性规则生成；
- 除 `JobFlow`、`AI Agent`、技能名称等必要专有名词外，说明文字统一使用中文；
- 文字简报之后单独发送城市岗位占比 PNG。

下列花括号内容是运行时模板变量，不是尚未确认的需求占位符：

### 11.6 首次真实发送后的格式微调边界

首次 Ubuntu 真实发送后，可以根据手机端截图微调空行、分隔线、字段顺序和固定措辞。微调不得改变日环比、周环比、岗位身份、薪资、技能、历史基准和真实岗位表达边界。

## 12. 城市岗位占比饼图

### 12.1 图表内容

饼图展示当天成功快照中上海、北京、杭州、深圳四个城市的岗位占比。

每个城市同时展示：

- 城市名称；
- 去重岗位数；
- 占当天总岗位数的百分比。

### 12.2 生成方式

使用服务器端 Python 图表库生成静态 PNG，不依赖浏览器界面。V1.3 优先使用 Matplotlib，以避免引入完整前端或 Telegram Bot 框架。

首版使用适合 Telegram 手机查看的方形 PNG。图片必须具备中文字体、清晰图例和可读配色；具体品牌色和高级排版在首版功能完成后迭代。

### 12.3 一致性检查

图表生成前必须验证：

```text
四城市岗位数之和 = 当天去重岗位总数
```

无法生成有效 PNG 时，不开始 Telegram 发送阶段，并将任务标记为简报生成失败。

## 13. Telegram 发送与重试

### 13.1 发送顺序

```text
1. sendMessage：完整文字简报
2. sendPhoto：城市岗位占比 PNG
```

继续使用现有轻量 HTTP 适配器，在现有 Telegram 通道上增加 `sendPhoto`，不为该功能引入完整 Telegram Bot 框架。

### 13.2 重试规则

- 文字发送最多尝试 3 次；
- 文字成功后，图片发送最多尝试 3 次；
- 只对网络超时、连接错误和可重试的服务端错误重试；
- 鉴权失败、参数错误等不可重试错误立即失败；
- 日志只记录 HTTP 状态、错误类型和尝试次数，不记录敏感值。

### 13.3 防重复规则

- 文字失败时，不发送图片；
- 文字成功、图片失败时，状态记为 `partial_failed`；
- 补偿重试只补发图片，不重复发送文字；
- 正式快照已成功后，消息重试不得重新抓取或覆盖快照；
- 已保存的 Telegram 消息 ID 用于判断已完成阶段。

## 14. 历史数据审计与回填

### 14.1 审计原则

上线前对 Ubuntu 中的 `ops.batches`、`raw.job_records` 和关联快照做只读审计。

历史日期只有同时满足以下条件才允许回填：

- 能关联到成功 ETL 批次；
- 能确认属于单一关键词 `AI Agent`；
- 能确认覆盖上海、北京、杭州、深圳四城市；
- 能确认每城页数和详情页模式；
- 原始岗位记录完整且可以按 `source + external_id` 去重；
- 不需要猜测缺失字段或日期。

### 14.2 回填行为

- 满足条件的日期生成历史快照头和岗位明细；
- 只有关键词、城市集合、每城页数和详情页模式全部一致的快照才能参与同一组日环比或周环比；
- V1.1/V1.2 已知的每城 1 页历史数据不得作为 V1.3 每城 3 页的增长基准；
- 回填过程必须幂等；
- 回填不触发 Telegram 推送；
- 不满足条件的日期跳过并记录原因；
- 如果没有安全可回填数据，从 V1.3 上线日开始积累。

历史回填是否可行只能依据服务器实际审计输出决定，不能依据文档快照提前宣称完成。

## 15. 异常处理与日志

日志必须明确区分：

```text
登录检查失败
城市抓取失败
快照校验失败
ETL 或数据库事务失败
对比计算失败
饼图生成失败
文字发送失败
图片发送失败
部分送达
完整成功
```

处理边界：

| 阶段 | 失败后的正式状态 | 是否保留旧数据 | 是否发送消息 |
| --- | --- | --- | --- |
| 登录或抓取 | 当天无正式快照 | 是 | 否 |
| Adapter/ETL/快照事务 | 整批回滚 | 是 | 否 |
| 对比或饼图生成 | 快照保留，简报失败 | 是 | 否 |
| 文字发送 | 快照保留，投递失败 | 是 | 否 |
| 图片发送 | 快照保留，部分送达 | 是 | 文字已送达，后续只补图片 |

## 16. 非功能与安全要求

- 保留现有任务锁，禁止同一时间运行两个每日更新任务；
- 每城 3 页任务必须在 systemd 现有超时边界内完成，首次真实运行后依据耗时证据决定是否调整；
- `.env`、Telegram Token、Chat ID、报告触发 Token、代理订阅、Cookie 和私钥不得写入 Git、PRD、日志或测试快照；
- Chrome CDP 继续只绑定服务器回环地址；
- 真实招聘数据不提交到公开仓库；
- 抓取行为遵守目标网站规则和适用法律；
- 每次统计必须可以追溯到快照日期、关键词和成功批次；
- migration、报告生成和回填脚本必须支持安全重复执行；
- 代码实现、离线测试、服务器部署和真实 Telegram 送达必须分别记录状态。

## 17. 测试设计

### 17.1 单元测试

必须覆盖：

- 正常日环比数量差和变化率；
- 缺少前一自然日；
- 前日值为 0；
- 跨月和跨年日期；
- 自然周周一至周日边界；
- 上一周不完整；
- 周内岗位去重；
- 新增采集、连续出现、本次未出现集合；
- 城市岗位数量一致性；
- 技能按岗位去重计数；
- 月薪区间中点与中位数；
- 日薪、时薪和无效薪资排除；
- 无有效薪资样本；
- 中文简报 4096 字符上限；
- 饼图输入数据一致性。

### 17.2 数据库集成测试

必须验证：

- migration 可在空数据库执行；
- 快照头与岗位明细正确关联；
- 同日同关键词正式快照唯一；
- 一个快照内岗位身份唯一；
- 四城市写入中途失败时事务全部回滚；
- 成功快照在消息重试时保持不变；
- 投递状态可以从文字成功推进到完整成功；
- 历史回填重复执行不产生重复记录；
- `search_keyword` 可以区分未来不同关键词的快照。

### 17.3 Telegram 离线测试

使用模拟 HTTP 响应验证：

- `sendMessage` 成功后才调用 `sendPhoto`；
- PNG 使用 Telegram 支持的文件上传请求；
- 网络超时和可重试 5xx 的重试次数；
- 不可重试 4xx 立即失败；
- 文字失败时不发图片；
- 图片失败时不重复文字；
- 消息 ID 和投递状态保存正确；
- 日志不泄露敏感信息。

### 17.4 脚本契约测试

必须验证每日脚本：

- 固定使用 `AI Agent`；
- 固定四城市；
- 使用 `--pages 3`；
- 使用 `--no-detail`；
- 任一城市失败时不进入合并、ETL 和推送；
- 已有成功快照且只需补偿消息时不会重新抓取；
- 退出码与日志状态一致。

## 18. Ubuntu 真实验收

按可独立验证的小步骤执行：

```text
1. 只读审计历史批次，形成可回填日期清单
2. 在测试数据库验证 migration 和可选回填
3. 手动执行一次四城市每城 3 页完整采集
4. 核对每城非空、总量和按身份去重结果
5. 核对正式快照头、岗位明细和关联批次
6. 人工抽查日环比、技能和薪资中位数
7. 生成并人工查看中文简报与 PNG
8. 手机 Telegram 真实收到文字
9. 手机 Telegram 真实收到饼图
10. 模拟图片失败并验证只补发图片
11. 创建一次五分钟临时 systemd timer
12. 验证无人操作时采集、入库、计算和图文推送全部成功
13. 检查 systemd 退出状态、耗时和日志
14. 删除临时 timer，保留正式每日 09:00 timer
```

不得只凭接口返回或 systemd 配置文本宣布验收成功，必须同时核对数据库、日志和手机 Telegram 实际送达。

## 19. 验收标准

### 19.1 数据验收

```text
四城市各 3 页抓取命令成功
四城市均返回非空真实岗位列表
当天岗位按 source + external_id 去重
正式快照与成功批次可追溯
任一城市失败时不产生正式快照
```

### 19.2 指标验收

```text
日环比与人工 SQL 抽查一致
缺失自然日不寻找替代基准
周日才展示完整自然周环比
周岗位按身份去重
技能按岗位计数
月薪中位数排除日薪和时薪
岗位变化使用“新增采集/连续出现/本次未出现”
```

### 19.3 推送验收

```text
文字简报不超过 4096 字符
文字先于图片送达
饼图数字与数据库一致
文字和图片均在手机 Telegram 真实可见
图片失败后补发不重复文字
```

### 19.4 自动化验收

```text
五分钟临时 timer 无人操作触发成功
任务锁继续有效
整批执行未超过 systemd 超时
日志能区分各失败阶段
本地 Windows 关机不影响 Ubuntu 服务器代理推送
```

## 20. 开发拆分原则

正式实施计划必须继续采用一次只推进一个可验证微任务的方式。建议拆分顺序为：

```text
1. 每日快照数据库模型与 migration
2. 快照写入和同日幂等规则
3. 日环比领域计算
4. 完整自然周领域计算
5. 中文简报格式器
6. 城市占比 PNG 生成器
7. Telegram sendPhoto 与分阶段投递状态
8. 每日脚本扩展为每城 3 页并接入新简报
9. 历史数据只读审计与条件回填
10. Ubuntu 手动真实验收
11. 五分钟临时 timer 验收

```

## 21. 已接受风险与后续方向

### 21.1 已接受风险

- 每城 3 页仍只是平台返回结果的一部分，不代表完整招聘市场；
- BOSS 登录态、验证码和风控仍可能使某天无正式快照；
- “本次未出现”无法证明岗位真实下线；
- 历史数据可能因证据不足而无法回填；
- 旧版每城 1 页历史数据与 V1.3 每城 3 页口径不同，不能直接用于 V1.3 环比；
- 首版图表先保证正确与可读，视觉包装后续迭代；
- V1.3 仍是单一关键词统计。

### 21.2 后续版本方向

- 将关键词、城市和页数配置化；
- 增加多个真实搜索关键词；
- 设计跨关键词岗位去重与分组简报；
- 增加浏览器数据看板；
- 在不改变确定性统计口径的前提下，可选接入大模型进行措辞润色或解释，并明确标注其生成边界。
