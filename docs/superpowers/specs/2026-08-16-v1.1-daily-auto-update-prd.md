# JobFlow V1.1：每日自动更新数据 PRD

## 1. 文档目的

本文档定义 JobFlow V1.1 的产品目标、使用场景、范围、自动更新流程、失败处理、验收标准和开发拆分。本文档只描述已确认的产品设计，不代表功能已经实现。

## 2. V1 当前基线

V1 已完成并在 Ubuntu 局域网环境真实验收：

```text
招聘快照
→ 手动上传 Ubuntu
→ Source Adapter 校验和标准化
→ ETL Worker 入库
→ PostgreSQL ops/raw/core/mart
→ FastAPI 查询接口
→ 中文报告生成
→ Telegram 私聊推送
```

当前 V1 的主要限制是：每天需要人工运行爬虫、上传快照和执行 ETL。

## 3. V1.1 目标

### 3.1 产品目标

让 Ubuntu 服务器每天自动运行现有的 `boss-zhipin-scraper`，自动抓取招聘数据、执行 JobFlow ETL、更新 PostgreSQL，并在成功后向 Telegram 私聊发送中文报告。

### 3.2 成功定义

用户不需要每天手动执行以下操作：

```text
启动爬虫
导出 JSON
上传 JSON
执行 migration
执行 ETL
手动调用报告接口
```

每日任务由 Ubuntu 自动完成，并且失败时不能把失败结果误当成成功数据。

## 4. 用户与使用场景

### 4.1 目标用户

当前目标用户是项目所有者本人，在个人 Ubuntu 服务器上查看招聘数据和 Telegram 报告。

### 4.2 主要场景

每天固定时间，系统自动完成：

```text
抓取 AI Agent 关键词下的上海、北京、杭州、深圳岗位
→ 更新数据库
→ 生成城市分析报告
→ 发送到个人 Telegram 私聊
```

## 5. 现有项目迁移策略

V1.1 不重写爬虫，直接迁移现有项目：

```text
Windows：<LOCAL_SCRAPER_DIR>
Ubuntu：<SCRAPER_DIR>
```

两个项目职责保持分离：

| 项目 | 职责 |
| --- | --- |
| `boss-zhipin-scraper` | 访问 BOSS、抓取岗位、生成 JSON |
| `JobFlow` | 校验 JSON、ETL、入库、分析、报告推送 |

爬虫项目 README 声明支持 Linux，但它通过 Chrome DevTools Protocol（CDP）连接已登录 Chrome。因此不能假设 Windows Chrome 登录态会自动迁移到 Ubuntu，Ubuntu 必须单独完成一次登录。

## 6. 目标运行架构

```text
systemd timer
        ↓
systemd service / 自动更新编排脚本
        ↓
Ubuntu Chrome Stable + Xvfb + CDP
        ↓
boss-zhipin-scraper
        ↓
临时 JSON 快照
        ↓ 校验成功后原子改名
JobFlow data/raw/inbox/boss_jobs_latest.json
        ↓
docker compose run --rm migrate
        ↓
docker compose run --rm etl
        ↓
PostgreSQL
        ↓
FastAPI /reports/cities/send
        ↓
Telegram Bot 私聊
```

### 6.1 Ubuntu 运行环境

服务器需要准备：

- Google Chrome Stable；
- Xvfb 虚拟显示；
- Chrome CDP 端口，默认只绑定 `127.0.0.1`；
- 爬虫 Python 依赖；
- Ubuntu 专用 Chrome 用户目录；
- systemd service；
- systemd timer。

首次配置顺序：

```text
安装 Chrome
→ 安装 Xvfb
→ 启动专用 Chrome CDP
→ 在 Ubuntu Chrome 中人工登录 BOSS
→ 保存专用登录目录
→ 手动抓取验证
→ 开启每日 timer
```

### 6.2 默认目录

```text
<USER_HOME>/services/
├─ boss-zhipin-scraper/
│  ├─ scripts/
│  ├─ data/
│  └─ local-output/
└─ jobflow/
   ├─ data/raw/inbox/
   │  ├─ boss_jobs_latest.json
   │  └─ archive/
   ├─ logs/
   ├─ compose.yaml
   └─ .env
```

## 7. 每日自动更新需求

### 7.1 默认调度

```text
执行时间：每天 09:00
时区：Asia/Shanghai
```

时间必须可配置，不应硬编码在业务代码中。

### 7.2 初始抓取范围

```text
关键词：AI Agent
城市：上海、北京、杭州、深圳
页数：沿用当前已经验证的参数
```

V1.1 先保持固定范围，避免同时引入关键词、城市和页数配置变化。

### 7.3 单次任务流程

```text
1. 获取任务锁，防止并发执行
2. 检查 Chrome CDP 是否可连接
3. 启动或复用专用 Chrome
4. 执行现有爬虫
5. 输出临时 JSON
6. 校验文件存在、JSON 合法、岗位数量大于 0
7. 将临时 JSON 原子改名为 boss_jobs_latest.json
8. 执行 migration
9. 执行 ETL
10. 验证批次 succeeded
11. 调用报告接口
12. 记录成功日志
```

## 8. 文件交接与数据安全

爬虫不能直接覆盖正式输入文件。应先写临时文件：

```text
boss_jobs_20260816.tmp.json
```

校验通过后再原子改名：

```text
boss_jobs_latest.json
```

如果抓取中断或 JSON 校验失败：

- 不覆盖上一份正式快照；
- 不执行 ETL；
- 保留错误日志和失败文件供排查；
- 不发送“更新成功”报告。

## 9. 成功与失败判定

### 9.1 成功条件

一次每日更新必须同时满足：

```text
Chrome CDP 可连接
→ 爬虫退出码为 0
→ JSON 格式正确
→ 岗位数量大于 0
→ ETL 退出码为 0
→ PostgreSQL 批次状态为 succeeded
→ API 能读取最新聚合结果
→ Telegram 收到报告
```

### 9.2 Chrome 或登录态失败

可能原因：Chrome 未启动、CDP 端口不可用、BOSS 登录过期或出现验证码。

处理方式：

```text
任务失败
→ 不执行 ETL
→ 保留旧正式快照和数据库数据
→ 写入日志
→ 不发送更新成功报告
```

V1.1 不自动绕过验证码，也不自动破解登录态。

### 9.3 爬虫失败

```text
保留旧数据
→ 不覆盖 boss_jobs_latest.json
→ 记录退出码和错误日志
→ 等待下一次任务重试
```

### 9.4 ETL 失败

```text
数据库事务 rollback
→ 批次标记 failed
→ 不发送成功报告
→ 保留原始快照供排查
```

### 9.5 Telegram 发送失败

```text
数据已经成功入库
→ 记录通知失败
→ 不回滚数据库
→ 日志明确“数据成功、通知失败”
```

数据入库和消息通知是两个阶段，Telegram 失败不应删除已经成功写入的数据。

## 10. 并发与重试

同一时间只允许一个每日任务运行，避免两个 Chrome、两个 ETL 或两条 Telegram 报告同时执行。

任务应具备：

- 任务锁；
- 明确退出码；
- 可查看的 systemd 日志；
- 失败后下一次调度自动重试；
- 不覆盖上一份有效快照；
- ETL 继续使用现有幂等 Upsert。

## 11. 安全与合规要求

- Chrome CDP 只绑定 `127.0.0.1`，不开放到公网；
- `.env` 权限保持 `600`；
- Telegram Token、Chat ID、报告 Token 不写入日志；
- BOSS 登录态只保存在 Ubuntu 专用 Chrome 用户目录；
- 真实招聘快照不进入 Git；
- 抓取行为遵守目标网站规则和适用法律；
- 日志只记录数量、状态和错误类型，不记录 Cookie、Token 或 Key；
- 不将“自动更新”描述为已经实现，必须以连续运行验收为依据。

## 12. V1.1 范围

### 12.1 必须实现

- 迁移现有 `boss-zhipin-scraper` 到 Ubuntu；
- 安装并配置 Chrome Stable、Xvfb 和 CDP；
- Ubuntu Chrome 完成一次人工登录；
- 每日固定时间自动抓取；
- 自动生成和校验 JSON；
- 自动执行 JobFlow migration 和 ETL；
- 任务锁和失败日志；
- 成功后调用 Telegram 报告推送；
- 连续多日真实运行验收。

### 12.2 明确不包含

- Telegram 中发送“今日总结”自动触发；
- 多用户权限和 Web 管理后台；
- 公网域名、HTTPS 和公网开放；
- 自动绕过验证码或破解登录态；
- 多服务器调度；
- PostgreSQL 自动备份、恢复演练、完整监控平台；
- 与本需求无关的数据库字段和业务重构。

## 13. 验收标准

### 13.1 环境验收

```text
Chrome Stable 安装成功
Xvfb 启动成功
CDP 端口可连接
Ubuntu Chrome 可以保持登录态
```

### 13.2 抓取验收

```text
四城市抓取成功
JSON 文件生成成功
字段符合 JobFlow 输入要求
岗位数量大于 0
```

### 13.3 ETL 验收

```text
migration 成功
ETL 成功
批次状态为 succeeded
数据库岗位数量更新
重复执行不会产生重复岗位
```

### 13.4 自动化验收

```text
systemd timer 能按时触发
任务日志可查看
失败任务不会覆盖旧数据
同一时间不会并发运行两次
```

### 13.5 业务验收

```text
Telegram 收到最新中文报告
报告中的城市数据与数据库一致
连续运行至少 3 天且每天结果可追溯
```

## 14. 开发拆分

V1.1 按以下独立微任务实施，每次完成后单独验收：

```text
1. Ubuntu 安装 Chrome、Xvfb 和 CDP 环境
2. 迁移 boss-zhipin-scraper 并完成手动抓取
3. 建立 scraper 到 JobFlow 的自动文件交接
4. 编写每日更新 Shell 编排脚本
5. 增加 systemd service
6. 增加 systemd timer
7. 测试失败、重试和任务锁
8. 接入每日成功报告推送
9. 连续多日真实运行验收
```
