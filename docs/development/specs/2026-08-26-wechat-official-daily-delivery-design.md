# OpenJobFlow 微信公众号每日推送设计

日期：2026-08-26
状态：已批准，待实施计划
范围：微信测试号模板通知、公众号文章排版包、独立渠道状态与每日任务编排

## 1. 背景与目标

OpenJobFlow V1.3.1 已经能够在 Ubuntu 上完成多关键词招聘快照、PostgreSQL ETL、趋势简报、PNG 图表和 Telegram 定时推送。Telegram 需要机器人 Token、接收目标和特定网络条件，公开仓库使用者不一定能够或愿意使用，因此项目需要增加一种面向微信生态的可选消息渠道。

本功能目标是：

1. 保留 Telegram，不替换现有渠道；
2. 通过微信公众平台测试号，每日自动向维护者微信发送聚合摘要模板消息；
3. 每日自动生成可用于个人订阅号的完整公众号文章排版包；
4. 个人订阅号首版由维护者人工确认发布；
5. 未来只有在正式账号实际具备草稿和发布接口权限时，才扩展全自动发布；
6. 微信失败不回滚 ETL，不阻止 Telegram 尝试，Telegram 失败也不阻止微信尝试；
7. 公开仓库只提供占位配置，不包含任何个人账号标识或凭据。

本功能版本定为 V1.3.2。完成本机离线验证、Docker 集成验证和测试号可行性验收后，才统一提交并推送公开仓库。

## 2. 已确认决策

| 项目 | 决策 |
| --- | --- |
| 账号主体 | 个人主体，无企业、个体工商户或组织资质 |
| 开发路径 | 先用微信公众平台测试号验证，再创建正式个人订阅号 |
| 微信呈现 | 自动模板摘要通知 + 完整公众号文章 |
| 正式文章发布 | 首版自动生成排版包，人工确认发布 |
| 公开数据 | 只展示聚合指标和趋势图，不公开原始岗位明细或岗位链接 |
| Telegram | 保留，与微信并行运行 |
| 渠道故障 | 独立记录、独立恢复，不互相回滚 |
| 正式发布 API | 只有账号后台实际显示具备权限时才设计和启用 |
| 浏览器自动化 | 不使用 Selenium、Playwright 等方式模拟公众号后台发布 |

开发前置准备已经完成到：测试号登录、接收微信关注测试号、测试模板创建。真实 `appsecret`、`openid` 和模板 ID 不写入本文、Git、日志或聊天记录。

## 3. 账号与发布策略

### 3.1 测试号阶段

测试号用于验证：

- 获取短期访问令牌；
- 模板消息负载；
- 单个接收者的真实手机送达；
- 定时任务、幂等状态和结果不确定处理；
- 公开配置模板是否足以让其他开发者自行接入。

测试号只承担聚合摘要通知，不承担正式公众号文章发布。

### 3.2 个人订阅号阶段

JobFlow 每日生成文章排版包，维护者登录公众号后台检查数据、封面、标题和趋势图后人工发布。这样不依赖个人订阅号未确认的 API 权限，也保留发布前的人为质量与合规检查。

若未来正式账号后台明确开放草稿与发布相关接口，则单独编写新设计，在不改变日报生成器的前提下增加正式发布适配器。首版不提前实现或宣传该能力。

## 4. 范围与非范围

### 4.1 本轮范围

- 微信公众平台测试号模板消息适配器；
- 统一多关键词日报数据模型；
- 微信模板字段映射；
- 公众号文章 Markdown、HTML、PNG 和元数据文件；
- 微信渠道独立数据库状态；
- 微信发送与状态查询 API；
- 每日 Shell 工作流并行尝试 Telegram 与微信；
- `.env.example`、Compose、双语 README 和运维文档；README 只做功能介绍并链接到详细配置教程；
- 离线测试、PostgreSQL 状态测试和一次真实测试号手机验收。

### 4.2 本轮非范围

- 正式个人订阅号全自动发布；
- 微信事件回调服务器；
- 公网域名、HTTPS、回调签名和事件解密；
- 多接收者管理界面；
- 用户注册、粉丝画像或营销自动化；
- 客服消息、一次性订阅消息或浏览器模拟后台；
- 原始岗位明细、岗位链接或个人简历数据公开；
- 改变招聘数据采集范围、ETL Schema 或现有 Telegram 恢复语义。

## 5. 总体架构

```text
多关键词快照与 PostgreSQL
          │
          ▼
统一多关键词日报构建器
├─ 聚合文字
├─ 趋势指标
├─ PNG 趋势图
├─ 微信模板字段
└─ 公众号文章数据
          │
     ┌────┴───────────────┐
     ▼                    ▼
Telegram 渠道        微信测试号渠道
文字 + PNG           模板摘要通知
     │                    │
     └──── 独立状态 ───────┘
          │
          ▼
runtime/reports/<日期>/wechat/
文章 Markdown + HTML + PNG + manifest
          │
          ▼
个人订阅号后台人工确认发布
```

Telegram 和微信调用同一个确定性日报构建逻辑，但保留独立发送服务和独立状态。任何渠道都不能直接读取原始抓取文件或任意 SQL；它们只消费已经聚合的日报数据。

## 6. 组件边界

### 6.1 `jobflow.channels.wechat_official`

职责：

- 验证微信配置是否完整；
- 获取短期访问令牌；
- 发送单条模板消息；
- 校验微信 JSON 回执；
- 返回不含凭据的统一回执；
- 将明确失败与结果不确定区分开。

该模块不查询数据库、不生成报告、不管理 systemd，也不把凭据写入异常文本。

建议公开接口：

```text
get_wechat_access_token(...)
send_wechat_template(...)
WechatReceipt(message_id, attempts)
WechatConfigurationError
WechatTokenError
WechatDeliveryError
WechatDeliveryUncertain
```

### 6.2 统一多关键词日报构建器

从当前 `multi_keyword_service` 中抽出纯构建逻辑，生成一个渠道无关的数据对象。Telegram 继续使用原有文字与 PNG；微信使用模板字段和文章字段。构建器不发送网络请求，不修改推送状态。

### 6.3 `jobflow.reports.wechat_article`

职责：

- 生成公众号文章标题、摘要和正文；
- 输出 Markdown 与静态 HTML；
- 复制或写出同一份 PNG 趋势图；
- 生成不含凭据的 `manifest.json`；
- 使用临时目录和原子替换，避免留下半套文章文件。

输出目录：

```text
runtime/reports/<YYYY-MM-DD>/wechat/
├─ article.md
├─ article.html
├─ trend.png
└─ manifest.json
```

`runtime/` 已被 Git 忽略。HTML 不包含脚本、远程跟踪资源、Token、openid 或原始岗位数据。

### 6.4 `jobflow.db.channel_deliveries`

使用新 migration 创建 `ops.report_channel_deliveries`，为微信等新增渠道提供独立幂等状态。现有 Telegram 快照投递字段保持兼容，不在本轮重写。

建议字段：

```text
id
report_date
report_key
channel
status
external_message_id
attempts
last_error_type
created_at
updated_at
```

唯一约束：

```text
(report_date, report_key, channel)
```

首版固定：

```text
report_key = multi_keyword_daily
channel = wechat_test_template
```

### 6.5 API

保留所有 Telegram 路由，新增：

```text
POST /reports/daily/multi/wechat/send
GET  /reports/daily/multi/wechat/status
POST /reports/daily/multi/wechat/resend?confirm_not_received=true
```

三个接口继续使用现有 `REPORT_TRIGGER_TOKEN` 保护。`resend` 只允许在调用者显式声明已经在手机中确认未收到消息时，将 `uncertain` 状态重新认领；普通 `send` 不会绕过结果不确定保护。

## 7. 模板消息数据契约

测试模板标题使用：

```text
JobFlow日报
```

推荐模板正文调整为：

```text
{{first.DATA}}
报告日期：{{report_date.DATA}}
样本记录：{{total_jobs.DATA}}
新增样本：{{new_jobs.DATA}}
需求最高：{{top_keyword.DATA}}
优势组合：{{top_city.DATA}}
{{remark.DATA}}
```

字段含义：

| 字段 | 口径 |
| --- | --- |
| `first` | 固定说明“JobFlow 多关键词日报已生成” |
| `report_date` | 快照日期，格式 `YYYY-MM-DD` |
| `total_jobs` | 四个关键词当前快照记录数之和；同一岗位命中不同关键词时按不同关键词样本分别计数，不能称为去重岗位数或全市场岗位总量 |
| `new_jobs` | 四个关键词相对前一自然日的新增记录数之和；同一岗位跨关键词分别计数；任一关键词缺少同口径基线时显示“基线建立中” |
| `top_keyword` | 当前快照记录数最高的搜索关键词；并列时按关键词文本升序取第一项 |
| `top_city` | 记录数最高的“关键词 / 城市”组合；并列时依次按关键词、城市文本升序取第一项 |
| `remark` | 固定范围和非全市场声明；周末可追加周对比摘要 |

模板值必须做长度限制和换行清理，不允许把异常文本、HTML、URL、岗位明细或凭据写入模板。

## 8. 公众号文章契约

文章只包含聚合数据：

1. 日期与固定范围说明；
2. 四个关键词的样本记录数与日变化；
3. 各关键词的优势城市；
4. 多关键词城市趋势图；
5. 如果当天是周日且完整两周基线存在，则追加周对比；
6. 数据口径、样本限制和“仅供学习研究”声明。

文章不得包含：

- 原始岗位标题列表；
- 公司名称；
- 招聘者信息；
- 原始岗位链接；
- Cookie、Token、openid、服务器地址或个人路径；
- “全市场”“实时全量”“官方统计”等无法由固定页数样本支持的表述。

## 9. 每日执行流程

```text
等待 API ready
→ 检查并补齐当天四关键词快照
→ ETL 与每日快照完成
→ 构建统一日报数据
→ 原子生成公众号文章包
→ 并行尝试 Telegram 与微信
→ 分别记录两个渠道结果
→ 汇总两个渠道状态
```

Shell 脚本可以并行启动两个发送步骤，并分别捕获退出码；即使一个渠道失败，另一个渠道仍必须完成尝试。任一渠道失败时，systemd 服务最终应返回失败，便于运维发现；已经成功的 ETL、文章包和其他渠道结果不得回滚。

同一天重跑：

- 已发送渠道返回 `already_sent`；
- 明确失败渠道允许修复配置后再次调用普通发送；
- `sending` 或 `uncertain` 渠道禁止普通重发；
- 文章包可以确定性重建，但必须原子替换。

## 10. 状态机与并发

```text
pending → sending → sent
                  ├→ failed
                  └→ uncertain

failed → sending       配置已修复后的普通重试
uncertain → sending    仅显式确认手机未收到后的 resend
```

Telegram 与微信是相互独立、可并行的渠道，各自维护独立状态。发送前使用数据库事务与行锁认领 `(report_date, report_key, channel)`；锁只阻止同一渠道同一天的重复发送，不阻止另一渠道并行发送。只有成功认领的请求可以调用对应渠道接口；同渠道并发请求返回已发送、正在发送或需要人工处理，不得同时发送两次。

## 11. 错误处理

### 11.1 配置错误

缺少任一必需变量时，不发网络请求，状态记录为 `failed`，`last_error_type` 记录 `wechat_configuration`。错误消息只包含缺少的变量名，不增加状态机之外的新状态。

### 11.2 访问令牌错误

获取访问令牌没有发送消息副作用，可以对网络错误和服务端错误做有限重试。微信明确返回无效凭据、IP 白名单或权限错误时立即失败，不输出请求 URL 或凭据。

### 11.3 明确投递失败

微信明确返回无效模板、无效接收者、用户未关注或无权限时，记录 `failed`。修复原因后允许普通发送接口再次认领。

### 11.4 投递结果不确定

模板发送请求发出后发生超时、连接中断、微信 5xx 或回执结构无法可信解析时，记录 `uncertain`。因为微信可能已经接收，首版不自动重试。维护者必须先检查手机，再决定是否使用显式 `resend`。

首版不实现微信回调服务器，因此不能宣称平台级最终送达确认。

## 12. 配置与安全

公开 `.env.example` 增加空占位符：

```dotenv
WECHAT_ENABLED=false
WECHAT_APP_ID=
WECHAT_APP_SECRET=
WECHAT_OPENID=
WECHAT_TEMPLATE_ID=
```

真实值只保存在部署者自己的服务器 `.env`，并保持权限 `600`。Compose 只把变量传入 API 容器。日志、状态接口、异常、测试快照和文章包均不得包含这些值。

微信 API 固定使用官方 HTTPS 域名，不提供通过环境变量任意替换 API Base URL 的公开接口，避免误配置和凭据外送。受限网络部署继续使用现有可选 Mihomo 出站配置。

## 13. 测试策略

### 13.1 渠道单元测试

- 缺少每个必需配置时不发送请求；
- 访问令牌成功、明确错误、网络重试和脱敏；
- 模板 JSON 负载与字段长度；
- 微信 `errcode=0` 成功回执；
- 明确错误码映射到 `WechatDeliveryError`；
- 超时、5xx 和异常回执映射到 `WechatDeliveryUncertain`；
- 异常文本不包含 appsecret、openid、模板 ID 或访问令牌。

### 13.2 报告与文章测试

- 模板字段来自固定聚合指标；
- 无前日基线时显示“基线建立中”；
- 周日完整基线才出现周对比；
- 文章包四个文件完整且可重复生成；
- HTML 无脚本、远程追踪和个人配置；
- 文章不包含原始岗位明细或链接；
- PNG 契约和虚构演示测试继续通过。

### 13.3 数据库与 API 测试

- 唯一约束和并发认领；
- `pending/failed/uncertain/sent` 状态转换；
- 已发送重复调用返回 `already_sent`；
- `uncertain` 普通发送被拒绝；
- 显式确认后只能补发一次；
- Bearer Token 保护和 HTTP 错误映射。

### 13.4 Shell 契约测试

- Telegram 失败后仍调用微信；
- 微信失败不改变已经成功的 Telegram 和 ETL；
- 两个渠道都成功时脚本退出 0；
- 任一渠道失败时两个渠道都已尝试，脚本最终退出非 0；
- `WECHAT_ENABLED=false` 时安全跳过微信，不影响默认复现路径。

### 13.5 真实验收

1. 使用虚构或当天合法聚合数据运行一次手动任务；
2. Telegram 收到一条文字和一张 PNG；
3. 微信测试号收到一条模板摘要；
4. 服务器生成完整公众号文章包；
5. 再次运行不产生重复消息；
6. 检查数据库状态、API 状态和 systemd 日志；
7. 确认 Git 差异和公开仓库秘密扫描无命中。

## 14. 验收标准

- 测试号手机真实收到定时模板摘要；
- Telegram 与微信均可独立开启或关闭；
- 一个渠道失败时另一个渠道仍被尝试；
- 同一天默认不会重复发送；
- 结果不确定不会自动重发；
- 公众号文章包包含完整聚合日报和趋势图；
- 文章只含聚合数据，并明确固定样本口径；
- 默认 Docker Quick Start 不需要任何微信配置；
- 公开 README 只介绍微信推送能力、默认关闭状态和安全边界，并链接到项目内的测试号配置教程；
- 详细测试号配置教程独立放在项目文档中，指导用户使用自己的凭据完成部署；
- 真实凭据未进入 Git、日志、测试、文档、截图或文章包。

## 15. 分阶段交付

### 阶段 1：离线契约

实现微信渠道、模板映射、文章生成、状态表与完整离线测试，不使用真实凭据。

### 阶段 2：本机与 Docker 集成

完成 Migration、API、Compose、Shell 和幂等测试，验证默认关闭微信时现有流程不受影响。

### 阶段 3：测试号真实联调

在服务器私有 `.env` 中配置真实值，单独验证令牌，再单独发送一条测试模板，最后接入每日任务。

### 阶段 4：正式个人订阅号

注册个人订阅号，使用 JobFlow 文章包人工发布。只有后台权限事实明确后，才决定是否另开“正式公众号 API 自动发布”设计。

## 16. 已接受风险

- 测试号不等于正式公众号发布能力；
- 个人订阅号可能没有草稿或发布 API；
- 首版没有微信事件回调，投递超时可能需要人工确认；
- 微信平台接口、模板规则和账号权限可能变化，真实联调前必须以当时后台能力为准；
- 固定页数招聘样本只能反映采样范围，不能代表整个招聘市场。

这些风险不会通过浏览器自动化、非官方接口或虚假能力描述规避。

## 18. 设计结论

### Summary

在不移除 Telegram、不公开个人配置且不假设个人订阅号具备发布 API 的前提下，为 OpenJobFlow 增加微信测试号定时摘要和公众号文章排版包。

### Chosen approach

采用渐进式双层方案：测试号自动模板通知，正式个人订阅号首版人工确认文章发布。该方案现在可验证、失败边界清晰，并为未来官方 API 自动发布保留稳定扩展点。

### Open risks

正式账号接口权限、微信平台规则变化、无回调时的结果不确定和固定样本口径已经接受，并通过能力边界、状态机和人工确认降低风险。
