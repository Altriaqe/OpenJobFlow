# OpenJobFlow V1.3.3 微信每日新增岗位公告设计

## 1. 背景

V1.3.2 已完成 Telegram 与微信公众号测试号的每日推送，并生成微信公众号文章排版包。现有微信内容以多关键词聚合趋势为主，不能在一篇文章中查看当天新增的具体岗位。

V1.3.3 将微信公众号文章包扩展为“每日新增岗位公告”：公众号入口使用一张横向封面图和固定标题“今日新增岗位”，文章正文展示当天相较前一日首次出现的全部岗位。Telegram 继续使用现有日报和趋势图，不修改内容、接口、状态机或调度方式。

## 2. 目标

1. 按搜索关键词列出当天全部新增岗位，不抽样、不截断。
2. 每个岗位展示现有真实字段，并链接到原招聘平台详情页。
3. 自动生成可供人工审核发布的微信公众号文章包。
4. 使用人工审核、人工发布的第一版流程，不依赖公众号自动草稿或发布权限。
5. 保持 Telegram 现有行为不变，微信文章失败不影响 Telegram 已完成的投递。

## 3. 非目标

- 不自动创建微信公众号草稿或自动发布图文。
- 不把测试号模板消息伪装成公众号图文卡片。
- 不新增招聘人数、报名时间、学历、经验或完整岗位描述等当前数据源没有的字段。
- 不修改 Telegram 文案、图片、API、状态机或去重逻辑。
- 不把真实岗位明细、快照、Cookie、Token、OpenID、AppSecret 或服务器配置提交到公开仓库。
- 不为详情链接在每日快照表中增加重复列。

## 4. 发布形态

公众号正式图文入口使用标准卡片样式：

```text
横向封面图
→ 标题：今日新增岗位
→ 点击卡片进入当天公告正文
```

日期、新增数量、关键词数量、城市数量和采集口径只显示在正文开头，不堆叠在入口卡片上。

测试号模板消息与公众号正式图文是两种不同能力。测试号可以继续验证 V1.3.2 模板链路，但不能作为正式图文卡片外观的验收证据。

## 5. 整体链路

```text
每日正式任务
→ 采集四关键词、四城市岗位
→ 写入当天岗位快照
→ 查找同关键词前一日同口径快照
→ 按 source + external_id 计算新增岗位
→ 联查 core.jobs.detail_url
→ 按关键词分组并稳定排序
→ 生成 Markdown、HTML、封面图、趋势图和清单
→ 保存到 runtime/reports/<日期>/wechat/
→ 等待人工审核
→ 人工复制到正式公众号后台并发布
→ 关注者看到“今日新增岗位”图文卡片
```

并行的 Telegram 分支保持不变：

```text
每日正式任务
├─ Telegram：沿用现有自动图文日报
└─ 微信：生成新增岗位文章包，等待人工发布
```

## 6. 新增岗位口径

岗位身份使用：

```text
source + external_id
```

对每个搜索关键词分别计算：

```text
当天岗位身份集合 - 前一日同口径岗位身份集合
```

同一岗位只修改标题、薪资、公司、城市或技能时，身份没有改变，不重复计为新增岗位。

可比较快照必须满足现有 `scope_key`：

- 搜索关键词相同；
- 城市集合相同；
- 每城市页数相同；
- 是否包含详情页的口径相同。

如果不存在前一日同口径快照，文章显示“基线建立中”，不把当天全部岗位称为新增岗位。

## 7. 数据字段

文章只消费项目已经采集和标准化的真实字段：

| 字段 | 文章用途 |
| --- | --- |
| `title` | 岗位名称 |
| `company` | 公司名称 |
| `city` | 工作城市 |
| `salary_text` | 展示原始薪资，如 `20-35K·14薪` 或 `面议` |
| `salary_min` | 薪资统计和稳定排序的可选输入 |
| `salary_max` | 薪资统计和稳定排序的可选输入 |
| `salary_unit` | 区分月薪、日薪和时薪 |
| `salary_months` | 表示 13 薪、14 薪等月份信息 |
| `skills` | 技能或岗位要求标签 |
| `detail_url` | “查看岗位详情”跳转地址 |

每日快照项已经保存岗位身份和公告所需的主要展示字段，但没有保存 `detail_url`。生成公告时使用 `source + external_id` 联查 `core.jobs` 读取 `detail_url`，不在快照表重复保存链接。

文章不显示“招聘人数”和“报名时间”。“当天新增岗位样本数”是快照差集数量，不等于企业真实招聘编制人数。

## 8. 文章输入模型

新增一个只服务于微信文章生成的不可变岗位摘要模型，职责是把数据库行与 HTML/Markdown 渲染隔离。建议字段为：

```text
source
external_id
keyword
title
company
city
salary_text
salary_min
salary_max
salary_unit
salary_months
skills
detail_url
```

微信文章顶层数据在现有 `WechatArticleData` 聚合趋势字段之外，增加按关键词分组的新增岗位集合。Telegram 不消费这个集合。

## 9. 文章结构

正文开头：

```text
2026-08-27 每日新增岗位公告

今日新增岗位样本：242
搜索关键词：4
覆盖城市：4
采集口径：每关键词 × 每城市固定 3 页
```

正文按关键词配置顺序分组：

```text
AI Agent · 新增 35 个
Python开发 · 新增 53 个
Java开发 · 新增 87 个
数据分析 · 新增 67 个
```

每个岗位使用独立卡片：

```text
AI Agent 应用开发工程师          20-35K·14薪
示例科技有限公司
工作地点：上海
技能要求：Python、LLM、Agent、FastAPI
查看岗位详情 →
```

岗位排序规则：

```text
关键词配置顺序
→ city 升序
→ title 升序
→ external_id 升序
```

当天新增多少就输出多少，不设置前 N 条上限。若公众号后台因长度限制无法发布，JobFlow 保留完整文章包并明确暴露总数，不静默删除岗位；拆分多篇文章属于后续版本。

## 10. 缺失值与安全处理

- `salary_text` 为空时显示“薪资面议”。
- `skills` 为空时显示“暂无明确技能标签”。
- `detail_url` 为空时不渲染“查看岗位详情”。
- `title`、`company` 或 `city` 为空时拒绝生成完整公告，避免发布残缺岗位。
- 岗位名称、公司名称、城市、薪资和技能必须进行 HTML 转义。
- `detail_url` 必须经过 URL 校验，只允许 `http` 或 `https`，并在生成 HTML 时进行属性转义。
- 详情链接是否仍有效，以原招聘平台实时状态为准。

## 11. 文章包

输出目录保持不变：

```text
runtime/reports/<YYYY-MM-DD>/wechat/
```

文章包从四件套扩展为五件套：

```text
article.md
article.html
cover.png
trend.png
manifest.json
```

`cover.png` 使用确认过的蓝色横向视觉，正文外部标题固定为“今日新增岗位”。封面使用项目现有 Matplotlib 无界面渲染能力确定性生成，不在每日任务中调用外部 AI 生图接口，也不依赖远程图片。这样本机、测试和 Ubuntu 可以用同一逻辑复现封面。

`manifest.json` 记录报告日期、文件清单、岗位总数、分关键词数量和图片哈希，不记录 Token、OpenID、Cookie、个人路径或岗位详情正文。

目录继续使用 `0755`，五个文件继续使用 `0644`，方便宿主机普通用户审核和复制。

## 12. 自动任务与人工发布边界

新增受 Bearer Token 保护的文章包接口：

```text
POST /reports/daily/multi/wechat/article/generate?snapshot_date=YYYY-MM-DD
GET  /reports/daily/multi/wechat/article/status?snapshot_date=YYYY-MM-DD
```

生成接口查询快照、计算新增岗位并原子生成五件套；状态接口只返回日期、是否存在完整清单、岗位总数、基线状态和生成结果，不返回岗位明细、文章 URL 或服务器绝对路径。

现有测试号接口 `/reports/daily/multi/wechat/send`、`status` 和 `resend` 继续保留，供 V1.3.2 手动联调和回归使用，但 `ops/daily_update.sh` 不再在正式每日任务中调用测试号发送接口。正式脚本改为并行运行：

```text
Telegram 自动发送
+ 微信 article/generate
```

每日任务只负责生成文章包，不声称文章已经发布：

```text
pending → generated
```

第一版不新增公众号文章 URL 回填接口，也不新增自动模板通知。`generated` 状态由完整、可校验的 `manifest.json` 和五个文件共同证明，不新增数据库 migration。人工发布状态由微信公众号平台管理，JobFlow 不在没有平台回执的情况下写入 `published`。

人工流程：

```text
打开 article.html 检查
→ 复制正文到正式公众号后台
→ 上传 cover.png
→ 标题填写“今日新增岗位”
→ 人工发布或群发
→ 手机端检查卡片、正文和岗位详情链接
```

## 13. 无新增岗位

存在有效前日基线但差集为空时，仍生成五件套：

```text
标题：今日新增岗位
正文：今日暂无新增岗位
趋势图和采集口径继续保留
```

是否在公众号发布由人工决定。文章中不生成空岗位卡片列表。

## 14. 失败隔离

以下情况使微信文章包生成失败：

- 当天任一必要关键词快照缺失；
- 数据库查询失败；
- 快照口径不一致；
- 必要岗位字段为空；
- `cover.png` 或 `trend.png` 生成失败；
- 文章目录无法写入；
- 原子替换文章包失败。

微信文章失败不得回滚或覆盖已经完成的 Telegram 投递。两个分支分别记录结果，Telegram 继续沿用现有去重和不确定结果恢复机制。

文章包继续使用临时目录加原子替换，避免审核者读到半套文件。失败时保留上一份完整包或不生成新包，不留下部分新文件。

## 15. 测试设计

### 新增岗位查询

- `source + external_id` 正确识别新增岗位；
- 同岗位修改标题或薪资不会重复计为新增；
- 不同关键词分别计算差集；
- 没有前日同口径快照时返回基线状态；
- `detail_url` 能从 `core.jobs` 正确联查。

### 文章渲染

- 四个关键词按配置顺序输出；
- 同组岗位按 `city/title/external_id` 稳定排序；
- 所有新增岗位均输出，不截断；
- 面议薪资、空技能和空详情链接正确降级；
- HTML 文本和 URL 属性正确转义；
- 无新增岗位时不生成空卡片；
- Markdown 与 HTML 的岗位数量和分组一致。

### 文章包

- 五个文件完整生成；
- `manifest.json` 数量和哈希正确；
- 覆盖生成继续保持原子性；
- POSIX 目录权限为 `0755`，文件权限为 `0644`；
- 公开敏感信息扫描通过。

### 回归

- Telegram 现有测试保持不变并通过；
- 微信测试号 V1.3.2 现有渠道单元测试继续通过；
- 微信文章失败不会改变 Telegram 投递状态；
- 非 integration 回归、Ruff 检查和格式检查通过。

## 16. 验收标准

### 本机验收

1. 使用确定性测试数据生成完整五件套。
2. 浏览器检查“封面图 + 今日新增岗位”入口样式。
3. 检查文章中所有测试新增岗位均出现一次。
4. 点击“查看岗位详情”能打开对应测试 URL。
5. Telegram 回归无变化。

### Ubuntu 验收

1. Ubuntu 从合并后的 `main` 拉取并重建 API。
2. 使用服务器真实的当天和前日快照生成文章包。
3. 普通用户无需 `sudo` 可读取五个文件。
4. 核对 `manifest.json`、正文岗位数量和数据库差集数量一致。
5. 人工复制到正式公众号后台，上传封面并发布。
6. 手机端看到“今日新增岗位”图文卡片。
7. 点击卡片打开完整公告，点击岗位链接打开原招聘平台详情页。

只有第 5 至第 7 项由用户实际确认后，才能记录为 V1.3.3 正式公众号图文验收完成。

## 17. 版本边界

V1.3.3 完成后可以表述为：

> OpenJobFlow 能基于前日快照差集自动生成包含当天全部新增岗位的微信公众号文章包，并支持人工审核后以标准图文卡片发布。

不能表述为：

> OpenJobFlow 已自动发布微信公众号文章，或已经具备完整公众号运营平台能力。
