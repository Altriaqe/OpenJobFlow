# 按日期按渠道投放工作台设计

## Summary

将现有 JobFlow Operations 中台的投放中心完善为可日常使用的运维工作台。管理员可以选择历史日期或当天，查看抓取、ETL、文章包、Telegram 和微信公众号草稿五段链路，并分别执行单渠道投放。

本阶段不重做中台、不引入多租户权限、不自动发布微信公众号文章，也不提供无确认的完整每日任务重跑。

## Goals

- 历史日期直接复用数据库已有快照，不重新抓取。
- 当天有可用快照时直接投放；没有快照时明确显示前置阶段未完成。
- 未来日期在前后端都禁止抓取和投放，并显示“未到时间”。
- Telegram 和微信公众号状态、动作、失败边界彼此独立。
- 已成功投放的渠道不可普通重复投放。
- 明确失败允许管理员再次投放。
- 结果不确定必须先由管理员确认外部渠道未收到，再允许恢复。
- 投放成功后页面能看到最新状态和时间。

## Non-goals

- 不把 Docker/API 服务重启和业务投放合并成一个按钮。
- 不自动重跑完整的抓取、ETL、报告和投放链路。
- 不自动发布微信公众号草稿，仍由管理员在公众号后台审核发布。
- 不改变 Telegram 结果不确定时的防重复原则。
- 不新增多租户、复杂角色系统或实时推送基础设施。

## User Flow

1. 管理员进入“投放中心”，选择一个日期。
2. 页面加载该日期的日期资格、快照/批次、文章包和两个渠道状态。
3. 页面展示五段链路：抓取、ETL、文章包、Telegram、微信公众号。
4. Telegram 和微信各自显示状态、最近更新时间、脱敏错误码和可执行动作。
5. 管理员只点击需要处理的渠道动作。
6. 操作返回后刷新该日期的状态，不影响另一渠道。

日期资格规则：

| 日期 | 快照存在 | 页面行为 | 后端行为 |
| --- | --- | --- | --- |
| 过去日期 | 是 | 可查看，可按渠道投放 | 复用快照，不抓取 |
| 过去日期 | 否 | 显示无可用快照 | 拒绝投放并返回明确业务错误 |
| 今天 | 是 | 可查看，可按渠道投放 | 直接复用当天快照 |
| 今天 | 否 | 显示数据未准备 | 不由投放动作隐式触发完整抓取 |
| 未来日期 | 任意 | 日期禁用并显示未到时间 | 拒绝抓取和投放 |

## State and Actions

### Channel states

- `not_sent`：没有成功投放记录，可执行投放。
- `sending` / `creating`：动作正在执行，按钮禁用。
- `sent` / `created`：渠道已成功完成，普通投放按钮禁用。
- `failed`：渠道明确失败，可执行再次投放。
- `uncertain`：外部结果不确定，不直接重试。

微信公众号使用现有语义：`created` 表示草稿已创建，之后的审核和发布仍在公众号后台完成。

### Action policy

| 状态 | 普通动作 | 恢复动作 |
| --- | --- | --- |
| 未投放 | 投放 | 无 |
| 投放中 | 禁用 | 无 |
| 已投放 | 禁用 | 无 |
| 明确失败 | 再次投放 | 无 |
| 结果不确定 | 禁用 | 先确认外部未收到，再允许恢复 |

确认不确定结果必须是显式请求参数，后端校验为真后才可进入恢复路径。恢复仍然限定为一个日期、一个渠道、一次动作。

## Architecture

优先复用现有边界：

- Streamlit `dashboard/app.py` 负责页面状态、日期选择和管理员操作入口。
- `dashboard/components.py` 负责链路条、状态卡片和动作按钮的展示，不执行 SQL。
- FastAPI `api/dashboard.py` 提供指定日期的统一只读投放快照。
- FastAPI `api/reports.py` 保留现有单渠道投放端点和管理员鉴权。
- `db.report_deliveries`、`ops.report_channel_deliveries` 和 `ops.wechat_draft_jobs` 继续作为状态来源，不在 Streamlit 内新增状态表。
- 现有幂等认领函数继续作为并发保护；前端按钮禁用只是体验层，不能替代后端判断。

统一快照至少包含：日期资格、抓取/快照是否存在、最新 ETL 批次、文章包状态、Telegram 状态、微信草稿状态、每个渠道的更新时间和脱敏错误码。

## Error Handling and Safety

- 未来日期、无快照日期、未完成文章包返回明确的 4xx 业务错误，不调用外部渠道。
- 已成功状态再次请求时，后端返回已完成状态，不调用外部渠道。
- 明确失败重试前重新执行幂等认领，不删除成功记录。
- 不确定状态默认拒绝重试，避免 Telegram 重复消息或微信重复草稿。
- 所有页面和 API 输出不得包含 Token、AppSecret、Webhook、Cookie、Chat ID、完整素材 ID 或完整请求 URL。
- 微信动作只创建草稿，不调用发布接口。
- Telegram 与微信失败互不回滚、互不重试。

## Verification

### Automated checks

- 日期资格判定覆盖过去、今天、未来以及无快照情况。
- 投放快照覆盖两个渠道的未投放、投放中、成功、失败、不确定状态。
- 已成功状态不会调用外部渠道。
- 明确失败可以再次投放。
- 不确定状态未显式确认时不会调用外部渠道；确认后只调用目标渠道。
- 未来日期和无快照日期不会调用抓取或投放函数。
- API 路由和 Streamlit 页面只通过既有服务/数据库边界工作。

### Manual acceptance

- 选择一个已有快照的历史日期，分别看到 Telegram 和微信状态。
- 选择一个已成功投放日期，两个渠道均不能普通重复投放。
- 选择一个只完成单渠道的日期，只能操作未完成渠道。
- 选择未来日期，页面禁用操作，后端请求也被拒绝。
- 制造或读取一个明确失败状态，确认可以单独重试。
- 检查不确定状态，确认未勾选确认项时不能恢复。
- 确认微信公众号仍需人工审核和发布。

## Open Risks

- 当前历史数据库中的 Telegram 和微信状态字段来自不同表，需要统一映射，不能简单按渠道最新行覆盖业务语义。
- “当天没有快照”是否允许管理员从中台显式启动抓取属于下一步功能，本设计先显示阻断原因，不隐式触发。
- Docker/API 服务重启操作保留为独立的运行中心能力，后续另行设计确认、权限和服务器执行边界。
